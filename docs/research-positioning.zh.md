# 研究定位：评测工具，还是科学问题

Glyph 面向谁、要回答什么问题，有两条可选路径。本文整理两条路径各自的叙事、需要的实验和下一步计划。
写于 2026-10-19，依据是 free protocol 的 18 个 run（2026-10-15）和之后去掉路径泄露的 8 个重跑。

本文和 `docs/motivation-real-world-tasks.zh.md` 是互补关系：那篇讲 Glyph 为什么要建、对应哪些现实任务；
这篇讲拿它去回答什么问题、面向哪个社区。

## 1. 现有证据：Glyph 实际在衡量什么

### 各部分的区分度

| 部分 | 实际测到的 | 区分度 |
|---|---|---|
| skeleton（structural 算子） | 所有 run 都在约 30 分钟内解完 | 低，接近天花板 |
| unary（3 × 4,913 cell） | query 不限量时只是"买不买"，测到的是工程执行，比如会不会用 subagent 并发买 | 低 |
| **binary（2 × 4,913² ≈ 4,830 万 cell）** | **agent 是否意识到这里要用归纳模型，并真的建出来** | **高** |
| train 和 no_train 两臂 | GPU 最多只被用了十几分钟；CPU 上的 numpy、sklearn 就够用 | 两臂之差主要来自 prompt 里的提示，而不是算力 |

binary 的四个解法层次：

| 层次 | 做法 | binary probe |
|---|---|---|
| L1 | 只查表或直接放弃 | ≈ 0 |
| L2 | 手推规则 | 0.01–0.51 |
| L3 | 非参数统计：计数表、多数表、kNN | 0.50–0.61，贴着逐位统计的上限 0.54–0.64 |
| L4 | 拟合模型：MLP、树模型、logistic | 0.64–0.83 |

只有 L4 能越过逐位统计的上限。

### 几条候选发现（目前样本都小，只能当方向看）

1. **规则偏好。** 证据已经表明不存在精确规则时，agent 仍倾向于继续找规则。
   例：`low_3` no_train 2h 准确诊断出 "out_k needs 4+ coords but data can't densely cover 17⁴ cells"，
   却把它当成天花板，提前结束。
2. **切换由提示触发，而不是由证据触发。**
   - 原 sweep 中，run 目录名带臂名（`low_3_no_train_tp1h`），agent 在每条消息里都能看到。
     `high_3` train 4h 明说 "Given the H100 GPU and "train" in the run name"。
   - 去掉路径泄露后，`low_3` 1h 的 L4 比例从原来的 train 1/1、no_train 0/1，变成 train 2/3、no_train 1/3。
3. **决策是瓶颈，算力不是。** 一旦决定要学，在 CPU 上用 numpy 或 sklearn 就能达到 L4。
   中性路径下 `low_3` 2h 两臂都到了 L4：train 用 GPU MLP 得 0.908，no_train 用随机森林得 0.859。
4. **可学性测试是关键动作。** 中性路径的 8 个 run 里，做过"这能不能学"测试的都到了 L4，没做的都没到。
5. **binary 的分量决定 agent 愿不愿意投入。** `high_3` 的 test 只有 757/10,000 题需要 binary，
   不做 binary 也能拿 0.924，所以两臂都没训练，这是理性的选择。`low_3` 有 3,214 题需要 binary。
6. **先验替代验证。** agent 能根据证据纠正自己，但这个能力不稳定，经常被一个先入为主的结论替代。
   最清楚的例子不在 binary 上，而在装 torch 上（见下一小节）。它和发现 1、2 是同一类现象：
   行为由先验和提示驱动，而不是由证据驱动。

### 同一现象在环境层面的例子：装 torch

旧镜像的 conda base 是 Python 3.14。torch 2.9 起才有 3.14 的 wheel，而 agent 最常用的 cu121、cu124 索引在那之前就停止更新了：

| 索引 | Python 3.12 | Python 3.14 |
|---|---|---|
| cu118 / cu121 / cu124 | torch ≤ 2.7.1 / 2.5.1 / 2.6.0 | 无 |
| cu126 / cu130，或默认 PyPI | 到 torch 2.14.1 | torch 2.9.0–2.14.1 |

在镜像里直接 `pip install torch` 是能成功的：耗时约 5 分钟，装上 torch 2.14.1+cu130。宿主机驱动 580 支持 CUDA 13.0，GPU 可用。
遇到安装问题的 6 个 train run 表现如下：

| run | 发生了什么 | 结果 |
|---|---|---|
| 原 sweep `low_3` train 1h | 没查驱动支持的 CUDA 版本，直接用 cu121 索引；失败后自建 py3.11 环境 | 恢复，用上 GPU |
| runs3 train 1h | cu121 失败，改用默认 PyPI，多等了一分钟 | 恢复 |
| runs5 train 2h | 发现装不上，自建 py3.11 环境 | 恢复 |
| 原 sweep `low_3` train 2h | 安装还在后台进行时就去 import，看到 `No module named 'torch._strobelight'`，断定 "torch has no working wheel for Python 3.14" | 放弃，改写 numpy MLP；run 结束时 torch 其实已经装好 |
| runs4 train 1h | 安装进行到一半时 import，报 `libtorch_global_deps.so` 缺失，随即 kill 掉安装进程 | 放弃，改写 numpy MLP |
| `mid_3` train 2h | 一看到 Python 3.14，就说 "torch wheels likely unavailable"，没有尝试安装 | 没试就放弃 |

前 3 个说明 agent 能根据环境调整。后 3 个的问题不是"不知道新版本"，而是用一个结论代替了验证：
没确认安装进程是否已结束，或者根本没试就下了结论。挑索引也是凭习惯，没有根据驱动版本去选：
agent 跑的 `nvidia-smi` 只查了显卡型号和显存，没看驱动支持的 CUDA 版本（13.0），就直接用了 cu121。

为了不让这类环境摩擦混进 binary 的测量，镜像已改为 Python 3.12（`glyph-free-py312.sif`，#81 上的 90865e0）。
这样无论用旧索引还是新索引都能装上。库仍然不预装，所以约 5 分钟的安装时间还在。

### 中性路径重跑（`low_3`，2026-10-15）

| T_p | train | no_train |
|---|---|---|
| 1h（3 次重复） | L3 0.819 / L4 0.871 / L4 0.878 | L1 0.679 / L4 0.858 / L1 0.680 |
| 2h（1 次） | L4 0.908 | L4 0.859 |

8 个 run 共花费 $1,260。no_train 两次放弃 binary，都发生在买 unary 卡住（第 37–40 分钟才拿到 0.636 基线）之后。

### silent 臂（`low_3`，2026-10-19，新环境：3.12 镜像、保留 validation 格子、绑核）

容器里有一块 GPU，但 prompt 和 README 没有任何环境描述。每个 T_p 三次重复：

| T_p | silent | 对照：`--no-bare-atomics`（裸调用返回 malformed，syntax 不提） |
|---|---|---|
| 1h | L2 0.685 / L1 0.680 / L3 0.775 | L1 0.680 / L3 0.781 / 失败 0.139 |
| 2h | L3 0.821 / L1 0.679 / L3 0.823 | L3 0.816 / L3 0.820 / L3 0.839 |
| 4h | L3 0.840 / **L4 0.872** / L3 0.801 | L3 0.837 / L3 0.819 / L3 0.804 |

- **18 个 run 没有一个探查过机器**：没有 `nvidia-smi`、`nproc`，GPU 占用全为 0。GPU 这件事只有被明说出来才起作用。
- **18 个里只有 1 个训练了模型**（CPU 上的 sklearn 树模型）。它是唯一一个在可学性测试为负时，把原因归为数据不够、估算所需样本量、补数据再测的 run。
- **禁掉裸调用没有改变任何行为**：agent 从第一分钟起就用 `s0` map 买 unary、用两元素 `s1` fold 攒 binary，量级和之前相同；没有任何 run 尝试过裸调用。数据渠道不是瓶颈。
- **一个测量上的发现**：`low_3` 的 `s1([x, y], b0)` 算的是 `b0(y, x)`。只通过 fold 接触 b0 的 agent，建出的表是 b0 的转置，fold 规则也跟着镜像，两者在所有结构化表达式上抵消，无法区分；只有裸的 probe 题会暴露方向。7 个有 binary 表的 nobare run 全部"反向"，probe 按原方向近 0，按反方向 0.37–0.59。report 现在同时记两个方向的 probe。
- **保留 validation 格子的副作用**：两个 agent 把拒绝信息读成了任务性质的线索，解读方向相反（"说明 binary 一定可学" vs "说明 binary 被设计成做不出来"）。
- 这 18 个 run 的环境和 2026-10-15 的 train / no_train 有四处不同，干净的三臂对比还需在新代码下重跑 train 和 no_train。

## 2. 路径 A：面向 agent / 评测社区 —— 一把新尺子

**核心问题**：Glyph 能否可靠地测出一种现有 benchmark 测不到的 agent 能力？

**叙事**：现有的 agent benchmark 大多事先告诉 agent 问题类型。MLE-bench、RE-Bench、PostTrainBench 说"去训练"，
SWE-bench 说"去改代码"，ARC 默认答案是一条规则。真实的开放任务没有这种标签。
Glyph 测的是：面对一个黑箱系统，agent 能否判断哪部分该推、哪部分该学，并把两部分都做出来。
它的题目程序化生成，instance 冻结，held-out test 只在 final 阶段出现，所以抗数据污染；π 可以调难度，不容易很快被刷满。

**这个社区关心的是测量质量**：

| 关心点 | 现状 |
|---|---|
| 效度：分数是否反映目标能力 | ⚠️ overall 里混了工程因素，比如 unary 买得快不快 |
| 信度：重复测量是否稳定 | ⚠️ 同一设置 1h 下分数在 0.68–0.88 之间 |
| 区分度：能否拉开不同模型 | ❓ 只测过一个模型（`claude-opus-4-8`） |
| 抗作弊 | ⚠️ 路径泄露已修（#82，0432dd9）；买下验证所需 cell 可让验证分饱和，还没修 |
| 成本和易用性 | ⚠️ 单个 run $30–530，完整排行榜需要数万美元 |

**主要风险**：成本太高，难以做成排行榜；下一代模型可能把它刷满。

**适合的发表渠道**：NeurIPS Datasets & Benchmarks、ICLR。

### 路径 A 的下一步

| # | 任务 | 说明 |
|---|---|---|
| A1 | 接入第二个模型 | harness 目前只支持 Claude Code CLI。要接 GPT、Gemini 或开源模型，需要一个与 CLI 无关的 agent 外壳，或者分别接各家的 CLI，并保证工具、提示、资源一致 |
| A2 | 修掉验证饱和 | query 拒绝验证题和 test 题所需的 binary cell，而不只是拒绝题目本身 |
| A3 | 让分数集中到目标能力上 | 两个选项：直接免费给出 unary 表，或者主指标改报 binary 层次加 headroom，overall 降为辅助指标 |
| A4 | 参考基线 | 只写规则的脚本 agent（L2/L3 上限）、会训练模型的脚本 agent（L4 参考），有条件再加人类专家 |
| A5 | 降低单 run 成本 | 缩短 T_p，限制 subagent 并发，或给每个 run 设美元预算 |
| A6 | 信度和区分度 | 每个 preset 用 `*_1`…`*_5` 五个 instance，每格 ≥3 次重复，报置信区间和跨 instance 的排名稳定性 |

## 3. 路径 B：面向 ML 社区 —— 何时推理，何时学习

**核心问题**：一个智能体在什么时候应该推理、什么时候应该学习？LLM agent 如何在两种模式间切换？

**叙事**：Glyph 把"能压缩成程序的结构"和"只能统计学习的结构"之间的界线做成了一个连续可调的参数 π，
这在真实任务里几乎做不到。在这个受控环境里，我们研究 agent 如何分配两种模式、什么触发了切换、切换的代价是什么。
这与神经符号方法、程序合成与神经网络之争、科学发现、系统辨识、归纳偏置等问题相连。

**产出是科学发现**，而不是排行榜。第 1 节列出的候选发现是这条路径的出发点。

**主要风险**：评审会问结论能否推广到 Glyph 之外，以及会提出"MLP 拟合 MLP 生成的函数"这类质疑。
需要用替换生成器（B4）和规则可解对照组（B1）来回应，并把结论限定为"受控条件下的现象"。

**适合的发表渠道**：ICML / NeurIPS 主会，reasoning 或 agent 相关的 workshop。

### 路径 B 的下一步

| # | 任务 | 说明 |
|---|---|---|
| **B1** | **规则可解的对照组（最优先）** | 造一批 binary 确实是打乱编码的 17 进制加法的 instance。这时理想的 agent 应该推出规则，而不是训练模型。同时测两类错误：该学时没学（漏报）、该推时去学（误报）。没有这个对照组，"方法选择能力"站不住 |
| B2 | π 剂量-反应曲线 | 把 π 细分成多档，画出"选择学习的概率"和 L4 比例随 π 的变化 |
| B3 | 提示干预（析因设计） | 因素包括：prompt 中有无 GPU；有无"可以训练模型"的提示；路径中有无臂名（已有 1 个数据点）；T_p 的长短。用来检验"切换由提示触发" |
| B4 | 替换生成器 | 把 table 换成决策树、有限域多项式、元胞自动机等，检验结论是否依赖"表本身是 MLP" |
| B5 | 过程编码自动化 | 把四层次分类、首次提到 ML 的时间、可学性测试的有无、各阶段用时，做成脚本自动从 transcript 中提取。手工版已有：`ml_first.py`、`belief.py`、`effort.py` |
| B6 | 重复次数 | 每个条件 ≥3 次，报告比例和置信区间 |
| B7 | 先验与证据（可选，独立于主测量） | 检验 agent 何时用证据纠正先验。例如在 binary 上，故意让某个看似可推的规则被少量反例否定，看 agent 多久放弃这个规则；在环境上，制造一个可恢复的安装障碍，看 agent 是验证后重试还是直接下结论。这类实验要和 binary 的主测量分开，不能混进同一个分数 |
| B8 | 实验设计效率的指标（零成本，用现有 run） | 现有指标只记"到了哪一层、最后多少分"，不记"问得好不好"。从 35 个 run 的 transcript 和 `queries.jsonl` 里提取：skeleton 解出的时间和用掉的查询数；依赖结构（输出第 k 位依赖哪些输入位）恢复的时间和正确性，可借用因果发现的结构距离来打分；binary probe 随已买格子数的学习曲线，把数据效率从最终分数里分开 |
| B9 | 理想贝叶斯基线（纯计算，不花 API 费） | skeleton 的假设空间有限，可以枚举出和已有查询一致的全部假设，选最能二分假设空间的下一个查询，得到最优实验者需要的查询数，作为 L2 的绝对参照。tables 一侧用生成器的真实先验（数字 embedding 加 MLP）做推断，得到"知道生成过程的学习者"在给定格子数下的上限，作为 L4 的参照。两者合起来给每个 instance 一个可达上限，比现有的简单天花板更有说服力 |
| B10 | 实验设计的价值（两个变体，排在 B1 之后） | 一是只观测、不干预：系统随机推送样本，agent 不能选输入，测"能设计实验"值多少；`--no-bare-atomics` 已经是在限制干预的粒度。二是给 query 一个小代价（不设硬上限），让主动采样重新有意义；这也是第 3 类应用（蒸馏）需要的成本旋钮 |

模型只需要 1–3 个，成本主要花在"条件 × 重复"上。

### 来自听众的视角（2026-10-19）

一次进展汇报后，听众把 Glyph 看成了一个主动推断和实验设计的测试台，关注"agent 怎么决定问什么"，而我们的分析集中在"agent 最后选了推理还是学习"。两个视角互补。几条评论和它们对项目的含义：

| 评论 | 和 Glyph 的联系 | 含义 |
|---|---|---|
| 像猜词游戏（Wordle、Mastermind） | 隐藏目标在有限假设空间里，每次提问得到结构化反馈，好的玩家选最能缩小空间的提问。这对应 skeleton，不对应 tables：binary 表不可压缩，问再多也只是采样 | 印证了 π 的两段划分：skeleton 是猜词游戏，tables 是统计学习；skeleton 上存在可计算的最优策略（B9） |
| 像因果机器学习 | agent 的受控查询是干预；"dependency arity" 分析是在恢复一张因果图。agent 把耦合项解读成进位，相当于用错误的因果模型解释残差 | 结构恢复可作为 L2 和 L4 之间的中间指标（B8）；"只观测、不干预"是一个自然的对照变体（B10） |
| 像贝叶斯优化：选下一个采样点，恢复未知函数 | 更贴切的名字是主动学习或最优实验设计。L4 的 run 几乎都是均匀随机采样；只有一个 run 估算过每个格子需要多少样本，没有任何 run 按不确定性挑采样点 | 学习曲线和主动采样基线（B8）；query 成本旋钮（B10） |
| 像概率编程 | 生成器本身是一个概率程序；agent 的任务是程序归纳加似然推断，和 Bayesian program learning 相关。35 个 run 里没有 agent 用过 Stan 或 Pyro 一类工具 | 理想贝叶斯 agent 作为基线（B9）；"告诉 agent 先验"是 B3 的一个延伸 |
| 数据分析问题：前沿模型什么时候意识到自己没有能力或工具（如 Turing、Stan、MCMC） | 这是"识别盲区、切换方法"在真实领域里的版本：模型知不知道该用 MCMC，比它会不会写 MCMC 更关键 | 第 4 类应用的一个具体形态：一组统计问题，有的靠推理能答，有的必须跑模型，测两类错误，结构和 B1 相同。Glyph 是抽象版，这会是具体版，两边用同一套指标 |

按性价比：B8 用现有数据，几乎零成本；B9 是纯计算；B10 排在 B1 之后。

## 4. 两条路径的对比

| | A：评测工具 | B：科学问题 |
|---|---|---|
| 一句话 | "这是一把新尺子" | "我们用这把尺子发现了 X" |
| 分析单位 | 模型 | 实验条件（π、提示、时间、生成器） |
| 主要产出 | 排行榜、协议、代码 | 现象、因果证据、机制分析 |
| 需要的模型数 | 多（≥5–8） | 少（1–3） |
| 关键缺口 | 多模型接入、降成本、修漏洞、提效度 | 规则可解对照组、替换生成器、干预实验、实验设计指标与理想基线 |
| 已有数据的价值 | 只是 pilot | 已有 6 条候选发现 |
| 成本 | 高 | 中 |

### 倾向

以 B 为主线，A 作为副产品：把协议和代码开源，自然就覆盖了评测社区。
理由是：我们手上最有意思的都是 B 类发现；B 需要的模型少，成本可控；"benchmark + 科学发现"是常见的论文结构。
B 成立的前提是先完成 B1。

## 5. 两条路径共同的近期步骤

不论选哪条路径，以下几件事都要做：

1. **更新 #84 的结果文档。** 加上路径泄露的说明，以及第 1 节的中性路径重跑结果。
   原 sweep 的 train − no_train 差值需要标为"受路径泄露影响"。
