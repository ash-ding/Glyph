What the frontier actually did

Splitting A0′'s items by whether the evidence contained the entries they needed separates two capabilities that a single score hides:

0.976 items whose needed entries were in the evidence 126 items
0.016 items whose needed entries were not 374 items

Retrieval saturated, extrapolation at zero. The frontier uses what it is told almost perfectly and infers almost nothing beyond it. That is not a capability shortfall — it is the separation the benchmark was built to produce.

The tail column is where that shows cleanly. Both arms have a tail of ~370 items — those needing entries never supplied — and on that subset the skeleton ceiling is 0.000, so every point is table knowledge. The frontier scores 0.016 there; a 1.7B student given a fifth as many entries scores 0.328. Twenty times, on exactly the items that require extrapolating.

The evidence was made deliberately generous — 2000 purchased queries revealing 2551 of 4913 unary entries, 70k tokens of it — so the failure does not depend on how much any particular agent happened to buy. Leakage was checked rather than assumed: the 2000 purchased expressions and the 500 scored ones intersect in zero rows.

One caveat, stated because it is the first thing worth checking: A0′ does not choose its own queries. The evidence was drawn by the harness, where a real agent probes adaptively. That does not touch the retrieval-versus- extrapolation split, which is about the evidence it was given; it does leave an adaptive-buyer control worth running.

Abstract

Given a verifiable task a frontier model cannot solve alone, when does putting capability into a small model's weights beat putting it into context or into code? And when an agent chooses for itself, how good is that choice?

Glyph is the instrument, not the answer. Each instance is a hidden interpreter whose syntax is public and whose semantics must be bought one query at a time. It splits deliberately into two halves that are different in kind: a skeleton sampled from a finite combinator grammar, which is always describable in finitely many words, and tables built from shared digit embeddings and frozen random MLPs, which are not. A single knob moves the difficulty between them, so the same generator produces instances where code should win and instances where only weights can.

How an instance is builtfrozen

generate(seed, cfg) runs five steps in order, each consuming a different part of the config from one seeded stream. Every step is a place a design decision lives.

  1. STEP 01 The value space data/grammar.py · data/tables.py

    A value is a fixed-length digit string, not an atomic symbol: dk(x) = ⌊x / basek⌋ mod base, giving 17³ = 4913 values rendered v_k_e_e. One random Gaussian vector is stored per digit position and value — 51 vectors, not 4913 — and a value's embedding is their concatenation. That sharing is the only reason an unqueried entry can ever be predicted.

    base = 17n_digits = 3d_digit = 16 value_form = letter_sep
  2. STEP 02 The skeleton — sampled, and describable data/semantics.py

    Each structural operator's meaning is drawn from a finite combinator grammar: ident · reverse · rotate k · dedup · take k · drop k · map_all · map_skip j, optionally under a guard. Sampling from a finite grammar is what guarantees the skeleton can always be written down in finitely many words — and every transform rearranges structure and never interprets a value, which is where the skeleton/table split comes from rather than being imposed.

    n_structural = 3 / 5 / 8max_transform_depth guard_prob
  3. STEP 03 The tables — learnable, not describable data/tables.py

    Never materialised. A table is a function: digits → shared embeddings → a frozen two-layer tanh MLP → decode to the nearest legal symbol. Tabulated it would be 4913 entries for unary and 24 million for binary. Operators are digit-wise with a weak global coupling term: pure digit-wise is enumerable into a lookup table, which hands the win to the code arm; too much coupling and nobody learns it.

    binary_coupling = 0.25unary_coupling = 0.25 mlp_temp = 1.0decode = whiten
  4. STEP 04 Held-out operator pairs data/instance.py

    A third of the directly-nested (outer, inner) operator pairs are kept out of the demo distribution, and the comp split then requires one to appear while every other split forbids all of them. Drawn only from pairs the grammar can actually build — an operator returning a value can never sit inside another — and a fixed share of each shape class, so the split's composition does not drift by seed.

    n_hold = |realizable| / 3
  5. STEP 05 Demos and the three splits data/instance.py

    Rejection sampling: draw an expression, test it against the split's constraints, keep or discard. Depth is sampled rather than being the split's budget restated — each recursion level may stop early, so iid spans depths 1–2 rather than sitting at a single point. A split that cannot be filled raises with a diagnosis rather than returning a short test set, which it used to do silently.

    depth_stop_prob = 0.15n_iid = 6500 n_comp = 2300n_depth = 1200

The order matters for reproducibility: every step draws from the same stream, so two configs that differ anywhere produce unrelated instances even at the same seed.

π — which half is the difficulty in?

The interpreter is P = skeleton ∘ tables, exactly two rule sets. Each crippled oracle is the real interpreter with one field swapped, which is what makes π measurable at all.

a_skel = accuracy(true skeleton + identity table) # only the table is missing a_tab = accuracy(trivial skeleton + true table) # only the skeleton is missing π = (1 − a_tab) / ((1 − a_tab) + (1 − a_skel)) # the SKELETON's share

π is a ratio against a chosen pair of baselines, so those baselines are fixed once and never changed. The trivial skeleton is textbook defaults rather than "do nothing" — if the structural operators did nothing, the atomic operators would never be invoked and the baseline would silently ablate the table as well.

A preset is a sampler, not a condition. Seven of twenty pi_mid seeds fall inside pi_high's measured range, so an instance at π = 0.70 cannot be attributed to a preset. Every run records its own measured π; figures key on that, never on the preset name.

Qwen3-1.7B, full fine-tune, lr 1e-4, 6000 steps, on one instance's tables across all five atomic operators. Skeleton ceiling on the same items: 0.248.

Extrapolation decays far more slowly than supervision. Ninety-eight entries — two percent of the table — still get 27.9% of the other 98% right. Going from 10% seen to 90% seen is nine times the supervision for a reach of 0.605 → 0.767. Samples constrain shared parts, not individual entries, which is the digit-embedding argument working harder than the design assumed.

An agent buys on the order of 10% of the table, so the band arms actually operate in is [0.248, 0.498] — 25 points, wide against the 1–3 point differences the arms are expected to be separated by. Two other readings from the same runs: fit is 1.000 at every point including at 98 entries, so capacity is never the constraint, generalisation is; and depth collapses fastest, being the most lookup-heavy split, which makes it the most sensitive cell on the phase diagram.

The agent's situation

An agent is given the syntax and 30 worked demos for free, and must buy everything else. Whatever it produces is then sealed and answers the test set with no further access to the oracle.

free

Syntax spec + 30 demos

Operator names are opaque — s0, u2 — so naming priors leak nothing.

metered

Query oracle

Evaluate expressions against the hidden interpreter. Malformed queries cost the same as well-formed ones.

sealed

The artifact

A prompt, a program, or a checkpoint. Sealing ends the prepare phase; nothing is reachable afterwards.

The armsin progress

Four containers for the same purchased knowledge. An arm is defined by which tools it is given, enforced in the harness rather than by asking the model to abstain.

ArmContainerWhat it sealsStatus
A0′none — frontier answers directly nothing; one shot per chunk measured
A2contexta prompt prefix, re-paid on every query rerun pending
A4codea Python solver, sandboxed, no network rerun pending
A6weightsa fine-tuned student, no prompt rerun pending
A7agent choosesany combination one row in the allocation table

Arm results are not published yet, deliberately. The earlier sweep is invalidated — the data layer changed underneath it — and two harness asymmetries that would have contaminated the comparison have since been settled rather than carried.

Only the weights arm had self-evaluation tools, so A2 wrote its prompt blind and sealed while A6 ran a full train–evaluate–inspect loop. Those tools are now universal: self-assessment is not a property of a container, and issuing it to one arm measured the harness instead. And the dev split is carved from the agent's own purchases, which do not match the test distribution — 91.5% of one run's queries were single-level against 12.5% of the test set. That is left in place, because an agent with a narrow probing strategy should get a misleading self-estimate, but every report now carries the gap and the distributions that explain it.

The arms are rerun once, on frozen instances, with one tool layer.

Evaluation protocolbeing settled

Scoring is exact match, one path for every arm, so a difference in the harness cannot masquerade as a difference in the container. Every score now ships beside the skeleton-only and table-only ceilings computed on the same items, because a raw number is not comparable across splits or instances — the skeleton ceiling alone ranges 0.148 to 0.744 across seeds.

Dev-time and test-time scoring share one path, so the number an agent steers on and the number it is graded by cannot drift apart — and the gap between them is reported rather than hidden.

Still to fix here: how many items each arm is scored on (pairing every arm on the same subset halves the standard error on a difference), and the query cap Q, which now also decides how clean the tail split is.

Experimentsplanned

The main figure is a (π, Q) phase diagram: where does each container succeed, as a function of where the difficulty sits and how much of the table the agent could see. Instances are sampled along a continuous π axis rather than grouped into three settings, since the presets' measured ranges overlap.

Also planned: a variance decomposition separating "some interpreters are harder" from "this run got lucky" — the two seeds are kept apart in the config for exactly that — and a second task where deployment is expensive by construction, which is what carries the amortisation argument Glyph cannot.

Layout

src/glyph/
├── data/          the data layer — makes an instance, never scores one
│   ├── config.py      GlyphConfig + presets (pi_low / pi_mid / pi_high / smoke)
│   ├── grammar.py     public syntax: AST, value codec, printer, parser, checker
│   ├── semantics.py   combinator grammar → skeleton; the trivial-skeleton baseline
│   ├── tables.py      digit embeddings, frozen MLPs, the identity-table baseline
│   ├── interp.py      P = Interpreter(skeleton, tables); lookup logging
│   ├── instance.py    generation, demos, query oracle, splits, tail derivation
│   └── measure.py     π via two crippled oracles
├── seal.py        one scoring path for every arm; ceilings and headroom
├── budget.py      the ledger — the single metered entry point
├── agent/         tool declaration · per-arm allocation · orchestrator
├── train/         full fine-tuning · vLLM inference
└── arms/          a2_context · a4_code · a6_weights · a0p_saturated

Nothing in data/ imports from outside it, and tests/test_data_boundary.py holds that line. The arrow runs one way — seal, agent and arms all import the generator — so the generator can be lifted whole into a second task without dragging along an evaluation protocol written for this one.

docs/progress.md is the append-only record of what was run and what it showed, corrections included. docs/open_questions.md is the standing list of what is still undecided, edited in place, with one GitHub issue per item.
