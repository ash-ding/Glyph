Glyph

A hidden-semantics DSL execution benchmark that evaluates how well frontier agents can build and use their own tools.

  1. RQ1

    Given a problem that inference-time scaling alone cannot solve, can a frontier agent identify the gap and train a small model as its own tool?

  2. RQ2

    How well can the frontier model use that tool?

Abstract

Glyph is a benchmark built to answer these questions. Each instance is a small programming language whose syntax is public and whose semantics are hidden inside an interpreter P. The only way to learn what an expression means is to ask P, one metered query at a time.

P has two halves that differ in kind. The skeleton — what each structural operator does to a list — is drawn from a small, finite grammar, so it can always be written down as code. The tables — what each atomic operator does to a value — are frozen random networks over shared digit embeddings, so they can be learned from examples but never written down. The presets move the difficulty between the two halves, and every instance carries a measured π that says where it ended up. The same generator therefore produces instances where reasoning and code should be enough, and instances where only a trained model reaches far.

The page follows that construction in order. Data generation builds one real instance step by step. Data validation measures it before any agent arrives: π, and the reference ceilings that frame every score. Evaluation protocol is how an agent meets it — a practice phase with a query budget and, in one arm, a small model it can train, then a single committed answer. Results will report when training pays off, and whether the agent knew.

Data generation

generate(seed, cfg) builds an instance in a fixed order, all from one seeded random stream. The first four steps define the language and the hidden interpreter P; the rest only decide which expressions are drawn from it. We follow one real instance — frozen instance mid_3, preset pi_mid, seed 1019 — and one of its demos all the way through. Every number below is exported from the generator, not typed by hand.

STEP 0

A preset and a seed

data/config.py · data/instance.py

A preset is a GlyphConfig: 22 fields, of which the three presets differ in five. The seed starts one random stream, and every later step draws from it in this order:

← interpreter Pdata drawn from P →

The order has a practical consequence. Change a knob that only shapes the data — atomic_ratio, say — and the same seed gives the same interpreter with different questions. Change a knob that shapes the language or the interpreter and the stream shifts from the start: the same seed gives an unrelated instance.

STEP 1

The value space

language + interpreter data/grammar.py · data/tables.py

A value is a fixed-length string of digits, not an atomic symbol: three digits in base 17 give 17³ = 4913 values, each digit written as a letter. The tables later need a vector for every value, and they get it by sharing: one random 16-dimensional vector per (digit position, digit) — 51 vectors in all — and a value's embedding is its three vectors concatenated. That sharing is the only reason an entry nobody queried can still be predicted.

Figure 1: one value of the example, from letters to digits to its 48-number embedding. Only 51 vectors exist; every value is built from three of them.

STEP 2

The public syntax

language data/grammar.py

The syntax is handed to the agent; nothing in it reveals what an operator does. Structural operators come from a fixed, public table of twelve, each with a shape — which arguments it takes and whether it returns a list or a value. Every block of four holds each shape once, and an instance enables a prefix of the table. Atomic operators are u0…u2 (one value in) and b0…b1 (two values in).

Enabled in pi_mid: the first 7. pi_low enables 5, pi_high 9. The shape names: UL (unary, list) → list · LB (list, binary) → value · L (list) → list · KL (int, list) → list.

      STEP 3
The skeleton — what each structural operator does

      interpreter
      data/semantics.py
    

    

      Each enabled structural operator gets a hidden meaning drawn from a small,
      finite grammar. Every primitive rearranges a list and never looks at what a
      value means; the only ones that touch the tables are
      map_all and map_skip,
      which apply the operator's unary argument. Fold-like operators then fold
      the list with their binary argument, left or right. A map-like operator
      must use its unary argument, an int-taking one its integer, and a pure one
      may not touch the table.
    


structural ::= transform
             | if guard then transform else transform        # chosen with probability guard_prob

transform  ::= ident | reverse | rotate k | dedup | take k | drop k
             | map_all u | map_skip u j                      # only in map-like (UL) operators
             | transform ; transform                         # "do A, then B" — 45%, while max_transform_depth lasts

guard      ::= len is even | len > k | first == last

fold-like (LB) operators add:   then fold the list with b, left or right (50/50)

    

    
Figure 2: how the hidden meanings of s0 and s1 were drawn — one grammar choice per step, each tied to the knob that weighs it.

    

      All seven hidden meanings of mid_3
      

    

    

      max_transform_depth = 2
      guard_prob = 0.5
      n_structural = 7
    

  


  
  

    

      STEP 4
The tables — what each atomic operator does

      interpreter
      data/tables.py
    

    

      A table is never stored. It is a function: split the value into digits,
      look up the digits' vectors, push them through frozen random MLPs, and
      round the result to the nearest legal value. Each digit position has its
      own small MLP — the digit-wise part — and one larger MLP sees the whole
      value; the coupling weight α sets how much of the answer comes from it.
      With α = 0 a unary table falls apart into 51 independent pieces (a binary
      one into 867) that an agent could enumerate; with α large nothing can be
      learned from a sample. Tabulated,
      a unary table has 4913 entries and a binary one about 24 million.
    

    

    
Figure 3: one unary and one binary lookup from the example, computed the way the generator computes every table entry.

    

      unary_coupling = 0.25
      binary_coupling = 0.25
      mlp_width = 64
      mlp_temp = 1.0
      decode = whiten
      d_digit = 16
    

    

      With steps 1–4 done, P is fixed. Nothing below
      changes what any operator does — only which expressions are asked about.
    

  


  
  

    

      STEP 5
Held-out operator pairs

      data
      data/instance.py · _draw_held_pairs
    

    

      A third of the directly nested (outer, inner)
      pairs are kept out of the demos, so the comp
      split can test compositions the agent has never seen. Only buildable pairs
      count — no operator takes a value argument, so a value-returning operator
      can never be the inner one — and the third is spread over every
      (outer shape, inner shape) class in proportion to its size, so which
      kinds of composition are held out does not depend on the seed.

      STEP 6
Sampling an expression

      data
      data/instance.py · _sample
    

    

      Expressions are grown top-down. Each node is asked for a type — a list or
      a value — and a depth budget. Below the root it may stop early and become
      a literal; otherwise it picks an operator of the right type. Where there is
      a choice, a coin weighted by atomic_ratio decides between the
      operators that consume a table (map-like, fold-like) and the purely
      structural ones. This one coin is what moves π most.
    

    

    
Figure 5: the example expression grown top-down. Blue nodes are structural operators; green slots name a table.

Demos and the three test splits

      data

Data validation


  

    Once an instance exists, it is measured before any agent touches it: one
    number that says where its difficulty sits, and a battery of reference
    oracles that say how far each kind of knowledge can get. Every score an
    agent later earns is read against these.
  


  
  
π — which half is the difficulty in?

  

    The interpreter is P = skeleton ∘ tables, exactly
    two rule sets. Each crippled oracle is the real interpreter with one half
    swapped for a fixed baseline, which is what makes π measurable at all.
  


  
a_skel = accuracy(true skeleton + identity table)     # only the table is missing
a_tab  = accuracy(trivial skeleton + true table)     # only the skeleton is missing

π = (1 − a_tab) / ((1 − a_tab) + (1 − a_skel))       # the SKELETON's share


  

    

      π is a ratio against a chosen pair of baselines, so those baselines are
      fixed once and never changed. The trivial
      skeleton is textbook defaults rather than "do nothing" — if the structural
      operators did nothing, the atomic operators would never be invoked and the
      baseline would silently ablate the table as well. π is the one place a
      lenient, per-digit grader is used; it keeps both losses from saturating
      near 1. Every score below is exact match.
    

    

      A preset is a sampler, not a condition. Five of twenty
      pi_mid seeds fall inside
      pi_high's measured range, so an instance at
      π = 0.70 cannot be attributed to a preset. Every run records its own
      measured π; figures key on that, never on the preset name.

How a score is reported

  
Every oracle and every arm reports the same four things, by exact match:

  

    

      
metricwhat it is

      
        
overallaccuracy over the scored items

        
by_splitthe same per test split — iid, comp, depth

        
tailaccuracy on items needing a table entry that was never seen or bought

        
headroom(score − skeleton ceiling) / (1 − skeleton ceiling): 0 means no better than knowing every structural rule and no table entry, 1 is perfect, and negative is kept, not clipped

      
    

  

  

    Oracles are scored on a paired subset: 500 test items per instance,
    stratified by split and seed-fixed, so every oracle on an instance answers
    exactly the same items. Arms are scored on the full 10,000 — the size that
    gives a standard error near 0.5%, enough to separate arms by 1–2 points.

      Extrapolation decays far more slowly than supervision. Ninety-eight
      entries — two percent of the table — still get 27.9% of the other
      98% right. Going from 10% seen to 90% seen is nine times the supervision
      for a reach of 0.605 → 0.767. Samples constrain shared parts, not
      individual entries, which is the digit-embedding argument working harder
      than the design assumed.
    

  


  

    

      An agent buys on the order of 10% of the table, so the band arms actually
      operate in is [0.248, 0.498] — 25 points, wide against the 1–3
      point differences the arms are expected to be separated by. Two other
      readings from the same runs: fit is 1.000 at every point including at 98
      entries, so capacity is never the constraint, generalisation is;
      and depth collapses fastest, being the most
      lookup-heavy split, which makes it the most sensitive cell on the phase
      diagram.

Evaluation protocol


  

    A run has two phases and compares two arms at equal stop conditions. The
    agent decides how to spend its budget, when to stop practising and whether
    to train; the harness only enforces the caps and meters the spend.
  


  

    

      phase 1
      
Practice

      
Given free: the syntax spec, 30 worked demos, and a visible validation set of 5,000 expressions without answers.

      
    
        
  • query — evaluate expressions against P. Metered, cap Q = 1000. Malformed queries are charged; queries that would read a validation or test item are refused and not charged.
    • 
        
  • submit — score an answer file on the validation set. Up to 20 times; returns only overall and a by-depth breakdown, never per item or per split.
    • 
        
  • check_answers — a free legality check of an answer file.
    • 
        
  • finish_practice — stop early.
    • 
        
  • train arm only: build_dataset, train, student_infer.
    • 
      

      
Ends at the 20th submit, on finish_practice, after 100 turns, at the $300 safety line, or after 3 idle turns.

    

    
→

    

      phase 2
      
Final

      
Revealed: the hidden 10,000-item test (iid, comp, depth) plus per-op probe items, with no answers. The oracle is gone.

      
    
        
  • check_answers — legality check against the test file.
    • 
        
  • final_answer — commit once. An illegal file is not committed and may be fixed; a legal one ends the run and is what gets scored.
    • 
        
  • train arm only: student_infer, to answer the test with a trained student.
    • 
      

      
At most 30 turns. The agent never sees a test score.

    The train arm's student is a Qwen3-1.7B model by default (the base model is

    continued or kept side by side.
  


  
Scoring a run

  

    

      The committed answers are scored by exact match against all 10,000 test
      items, with the same four metrics as the oracles, plus a by-depth
      breakdown and headroom on every split. A run
      that ends without committing has its last legality-checked test file
      committed for it; with neither, it scores zero. Per-op probes are scored apart from
      overall, each op split into cells the run did
      and did not buy. The report also carries the validation-versus-test gap —
      never shown to the agent mid-run — and the run's spend: queries,
      submissions, turns, model tokens and GPU seconds, all through one ledger.
    

  

  

    

      
splitnwhat it tests

      
        
iid6500in-distribution, held-out pairs forbidden

        
comp2300compositional generalisation: requires a held-out operator pair

        
depth1200deeper than anything in the demos

        
tailderiveditems whose table entries this run never bought — derived per run, because "never seen" is only knowable afterwards

What will be reported here.

    

      The main figure is a (π, Q) phase diagram: where each arm succeeds, as a
      function of where the difficulty sits and how much of the table the agent
      could buy. Instances lie along a continuous π axis rather than in three
      groups, since the presets' ranges overlap.
    

    

      Alongside it: the train arm against the no_train arm at matched coverage,
      read as headroom over the reference ceilings; whether the agent's own
      choice to train, or not, was the right one; and a variance decomposition
      separating "some interpreters are harder" from "this run got lucky".
